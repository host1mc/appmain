# Security matrix — verdicts

Every row of the defence-in-depth matrix, judged against the code as it stands
after this pass. Verdicts are from reading the source, not from running it: the
Oracle ATP this repo points at is the live shared production database, so
verification here is `ast.parse`, grep and reading, never a connection or a test
run.

`/admin` is excluded by instruction and was left exactly as it was.

Legend — **PASS**: implemented and verified in code. **PASS (infra)**: correct,
but enforced outside this repo. **PARTIAL**: implemented with a stated limit.
**OPEN**: not done, with the reason.

Configuration legend — a verdict says whether the code is *right*, not whether it
is *switched on*. Those are different questions and this document used to answer
only the first, so every control now also carries one of:

- **[ACTIVE]** — on with nothing set in the environment. This is what an
  unconfigured deployment actually gets.
- **[INERT: `VAR`]** — the code is present and correct and does nothing at all
  until `VAR` is set. The variable is named exactly, every time.
- **[PARTLY ACTIVE: `VAR`]** — on, but weaker than the prose reads until `VAR`
  is set.

That distinction is the reason for this pass. The previous version described
defences that ship switched off in the same voice as defences that are running,
which is worse than not describing them at all: it invites an operator to count
on a control that is not there. Every inert one is also collected under
[Controls that are inert by default](#controls-that-are-inert-by-default).

## 🖥️ Frontend

| Security | Where | Verdict |
|---|---|---|
| CSP | response headers | **PASS** **[ACTIVE]**, two distinct policies. Flask tier: `script-src 'self' 'nonce-{nonce}' 'strict-dynamic' 'unsafe-eval'` plus ad hosts, `style-src 'self' 'unsafe-inline' https://fonts.googleapis.com`, `frame-ancestors 'none'` (`frontend.py:_security_headers`, the policy built at :1010-1104). `https://fonts.googleapis.com` is used by third-party ad rendering — a stylesheet is fetched at runtime, and without the host there those requests are refused — while `font-src 'self' https://fonts.gstatic.com`, where those font files come from, is load-bearing for our own type as well (`static/style.css:12` @font-faces Inter off it and no font file is self-hosted anywhere in the tree). The interstitial in `edge_gate.py` carries its own nonced CSP because it is emitted from WSGI and gets neither tier's header set (`edge_gate.py:676-724`). |

| frame-ancestors / X-Frame-Options | response headers | **PASS** **[ACTIVE]** — panel sends `X-Frame-Options: DENY` (`panel_app/security_headers.py:48`); both tiers carry `frame-ancestors 'none'` in CSP. |
| Referrer-Policy | response headers | **PASS** **[ACTIVE]** — `no-referrer` on both tiers (`frontend.py:974`, `panel_app/security_headers.py:50`), chosen because session and server ids appear in panel URLs and would otherwise leak to every off-site link the page carries. |

**Also fixed in this layer this pass:** the panel's unhandled-500 path carried no security headers at all. Starlette's `ServerErrorMiddleware` is installed *above* the whole user middleware stack, so a 500 never unwound through `PanelSecurityHeadersMiddleware` — the one response an attacker can most easily provoke was the only one with no CSP, no nosniff and no HSTS. The header set was extracted into `apply_panel_headers()` and an `Exception` handler now applies it directly and returns a fixed body, so no exception text leaks the internal host, path or query.

## 🔌 API

| Security | Where | Verdict |
|---|---|---|
| CORS allowlist | backend / reverse proxy | **PASS by construction** **[ACTIVE]** — no CORS middleware and no `Access-Control-Allow-*` header is emitted anywhere in the tree. With no CORS headers the same-origin policy is already the allowlist; adding a permissive one is the only way to get this wrong. |
| WebSocket origin (CSWSH) | `panel_app/routes.py` | **PASS** **[ACTIVE]** — **fixed this pass.** CORS never applies to a WebSocket handshake and the browser attaches the host-scoped session cookie to it whatever page opened it, so `console_ws` accepted a socket from any origin and streamed a signed-in visitor's container logs to it; SameSite=Lax was the only obstacle, and nothing in the handler looked at `Origin`. `_ws_origin_allowed` (`routes.py:204-247`) now refuses a handshake whose `Origin` host:port is neither the request's own `Host` nor `PANEL_MAIN_SITE_URL`, and a missing `Origin` with it — browsers always send one on a handshake. Same-origin is the panel's existing arrangement, not a new constraint: the session cookie is host-scoped, so it only reaches `/panel` when `/panel` is served from the site's host. Only host:port is compared, never the scheme, because a TLS-terminating balancer forwards a plain-HTTP request whose `Origin` still reads `https` — matching schemes would refuse every console behind one. The check runs **before** `resolve_flask_session`, so a cross-site attempt buys no backend call and no Oracle read. The socket is write-only (no `receive_*`), so the exposure was read-only log exfiltration rather than command injection into a container. |
| Authentication | backend | **PASS** **[ACTIVE]** — the panel has no login of its own. It reads the Flask session cookie, resolves it through the backend's internal-only `GET /api/session/<sid>` (`backend.py:api_get_session`, :922-945) behind a shared `X-Internal-Token`, and mirrors the identity into `panel_users` with the unusable placeholder hash `external:oracle`. Every call into the backend is a **read**, so a bug in the panel cannot create, extend or destroy a session. Missing internal token fails **closed**, and as a 503 rather than a redirect to a login that could not authenticate either (`panel_app/auth.py:421-425`). |
| Authorization / RBAC | backend | **PASS, and load-bearing** **[ACTIVE]** — the node agent performs **no ownership check of any kind**: one shared bearer token, and it resolves a server purely from its `dchost.server_id` Docker label. The application tier is therefore the only authorization layer that exists, and every panel route filters by an owner id. **Fixed this pass:** `admin_delete_user` removed every `panel_servers` row without telling the node, leaving containers permanently unreachable through the panel while still holding node CPU, memory and disk — the node was the only thing that still knew they existed. Containers are now torn down first and the whole delete refuses on any non-404 node failure rather than orphaning them. |
| Rate limiting | backend / reverse proxy | **PASS** **[PARTLY ACTIVE: `RATELIMIT_STORAGE_URI`]** — flask-limiter is *not* the whole abuse defence any more; the per-IP shedder in `edge_gate.py` sits in front of it in WSGI (see the Internet layer) precisely because a request that flask-limiter answers 429 has already paid for a session resolve. Within flask-limiter, the credential-stuffing gap is closed this pass. `/user/login` was limited per-IP only (`10 per minute`, `frontend.py:2209`), so a run spread over a botnet stayed under the limit from every address while making unlimited attempts at one account. A second limit now keys on the **targeted account**: `30 per hour` over a SHA-256 of the casefolded username (`frontend.py:2210-2216`, key at `_login_target_key` :2064-2095), so all attempts at one account share a bucket regardless of source. The key is hashed because bucket keys are written to the shared store and usernames are encrypted at rest everywhere else in this tier. `deduct_when=_login_attempt_failed` (`:2097-2109`) charges only failures, so a successful sign-in never spends the allowance. Known trade-off, deliberately accepted: any per-account limit is also a lockout primitive, which is why the ceiling is set where a real person will not reach it and a stuffing run will. **Panel — corrected this pass, the old numbers were obsolete:** the panel limiter is no longer GET-exempt. `RateLimitMiddleware` keeps **two separate buckets** per identity in one 60 s fixed window — `max_requests=60` for mutating verbs and `get_max_requests=600` for `GET`/`HEAD`/`OPTIONS` (`panel_app/security_headers.py:155-156`, the split and the `r:`/`w:` key prefixes at :222-227). Separate buckets, not one counter against two ceilings, so cheap reads cannot spend the mutating allowance. Both ceilings are **hardcoded defaults with no env override** — `panel_app/__init__.py:188` passes only `trust_proxy` — and counters are per-process, so with two instances the fleet-wide ceiling is twice each number. Eight node-cost operations carry a far tighter per-user throttle on top (`panel_app/routes.py:_THROTTLES`, :107-116 — 3 reinstalls / 5 min, 6 extracts / 5 min, and so on). **Also fixed this pass:** the internal `GET /api/session/<sid>` carried no explicit limit, so it spent the shared `default_limits` (`500 per minute` per IP, `backend.py:190`). The frontend forwards the visitor's `X-Forwarded-For` so its lookups key per visitor, but the panel sends none and resolves the session *before* its own limiter can count it — `FlaskSessionMiddleware` is registered outside `RateLimitMiddleware` (`panel_app/__init__.py:185` vs `:188`), so the resolve happens first whatever the verb, which is why fixing the GET exemption did not close this. That collapsed every panel lookup onto one source address that exhausts the 500/min budget in seconds, after which every panel page 503s. The route now carries an explicit `2000 per minute` (`backend.py:api_get_session`, the limit at :944; Flask-Limiter's `override_defaults` defaults to `True`, so this replaces the shared default for this route only). Raising the admission cap still cannot worsen pool pressure, but **not for the reason previously given**: peak concurrent lookups are bounded by the tier's thread count — 8 waitress threads (`backend.py:2071`) or 2 gunicorn workers × 4 threads (`main.py:118`) — not by the rate limit, so the limit was never the binding constraint and raising it adds no concurrency. What is *false* is that those threads match the pool: the backend tier gets 4 Oracle sessions per process (`database.py:75`, `_ORACLE_POOL_MAX_BY_TIER`) and 2 per worker under gunicorn (`main.py:144`, `_GUNICORN_POOL_MAX`) — **2 threads per connection either way, a 2:1 oversubscription, not a match.** So at saturation roughly half the threads are queued on `pool.acquire()` rather than each holding a slot. The conclusion survives; the honest version is that pool waiting is this tier's normal saturation mode rather than an anomaly, and what keeps a 2:1 ratio queueing instead of deadlocking is that `get_session` never demands two slots at once — it closes the `SELECT` connection in a `finally` before acquiring the one for the `UPDATE` (`database.py:get_session`, :1684-1725). |
| Input validation | backend | **PASS** **[ACTIVE]** — `_valid_sid` is the sharpest instance: the cookie is interpolated into `/api/session/{sid}` and sent with the internal bearer token, so hex-only validation is what stops a visitor choosing the path of a privileged internal request. Mirrored identically in both tiers by explicit contract (`frontend.py:_valid_sid`, :302-313; `panel_app/auth.py:_valid_sid`, :173). Form fields are separately bounded before anything is forwarded or hashed (`frontend.py:FORM_FIELD_MAX`, :457-465). |
| CSRF protection | backend | **PASS** **[ACTIVE]** — the panel never mints a token; it reads the main site's token out of the session, since minting would mean writing to the live session store and would hand the browser a token the main site does not recognise. The Flask-side comparison is `_tokens_equal` (`frontend.py:286-299`). |
| Request size limits | backend / reverse proxy | **PASS** **[ACTIVE]** — and true on **both** tiers as of this pass, which it was not when this row was first written. Both read the same variable, `PANEL_MAX_CONTENT_LENGTH`, and both clamp it identically to 150 MB default / 1 MB floor / 512 MB ceiling, so a malformed or hostile value can neither widen nor collapse the cap: the panel through `_clamped_int` (`panel_app/config.py:193-198`, helper at :65-70) and the Flask tier — the one that actually receives the uploads — through `_env_clamped_int` (`frontend.py:424-425`, helper at :84-89). Both helpers swallow a non-numeric value back to the default rather than raising at import. Two tighter inner caps sit under that ceiling for paths that have no business being large: `API_MAX_BODY_BYTES` (`frontend.py:440`, default 1 MiB) and `FORM_MAX_BODY_BYTES` (`:449`, default 1 MiB), the latter because `_check_csrf` reads `request.form` before any view runs. ## 🔑 Passwords

| Security | Where | Verdict |
|---|---|---|
| Argon2id | backend, before DB storage | **PASS** **[ACTIVE]** — `time_cost=2, memory_cost=19456 KiB, parallelism=1, hash_len=32, salt_len=16, type=Argon2id`, which is OWASP's baseline, with PBKDF2-HMAC-SHA256 retained for hashes already stored and for any tier where `argon2-cffi` is not importable. That is a deliberate choice — a Cloudflare outage locking every user out of the site and the panel is judged worse than the flood — and the asymmetry is honest: only a *transport* failure fails open, a token Cloudflare actively rejects is `False` regardless of the flag (`:174-176`). ## 🍪 Sessions

| Security | Where | Verdict |
|---|---|---|
| Secure cookies | backend cookie settings | **PASS** **[ACTIVE]** — `secure=_cookie_secure()`, which follows the scheme actually in use rather than being hardcoded `True`. Hardcoding it breaks login on the http:// dev box in the worst possible way: a `Secure` cookie is simply never sent, so login appears to succeed and every subsequent page is signed out again, with nothing in the logs. `COOKIE_SECURE` forces it for a deployment that terminates TLS somewhere this cannot infer (`frontend.py:267-274`). |
| HttpOnly | backend cookie settings | **PASS** **[ACTIVE]** — `httponly=True` on every `set_cookie` in the session interface (`frontend.py:379-418`). |
| SameSite | backend cookie settings | **PASS** **[ACTIVE]** — `samesite="Lax"` throughout. |
| Cookie authenticity (HMAC) | `session_cookie.py`, both tiers | **PASS** **[ACTIVE]** — the cookie carries an HMAC-SHA256 tag over the session id, compared with `hmac.compare_digest` (`session_cookie.py:206`), truncated to 128 bits and base64url-encoded as `<sid>.<tag>` (`:136-151`). One shared standard-library leaf module signs and verifies for the whole fleet — `open_session` and `save_session` in the frontend (`frontend.py:343-344`, `:408-409`, plus `_session_id` at `:147-148`) and `resolve_flask_session` in the panel (`panel_app/auth.py:415-418`) — so the two tiers cannot disagree about what a valid cookie is. The key is derived, domain-separated, from the shared internal token rather than the per-instance Flask secret (`:127-133`), which is what lets a cookie signed on instance A verify on instance B with no new variable to forget on one host. Why it matters: `open_session` runs at request-context push, *before* flask-limiter and before every `before_request`, so a random hex cookie used to buy a backend HTTP call plus an Oracle SELECT that no rate limiter could refuse — the cheapest way to exhaust a ~20-session Always Free ATP. A forged cookie is now rejected with **zero I/O**, and that includes an untagged one: `SESSION_COOKIE_MAC_GRACE` now defaults **off** (`:119-129`), so the omit-the-tag route into the amplifier is closed. Set `SESSION_COOKIE_MAC_GRACE=1` only for the span of a rollout that must keep honouring pre-deploy cookies while they are re-issued with a tag. `SESSION_COOKIE_MAC=0` disables the mechanism entirely as an escape hatch (`:113-115`). |

**Fixed in this layer this pass:** the panel's per-request session resolution had two defects. Its static-file skip tested `scope["path"].startswith("/static")`, but `Mount` does not rewrite `scope["path"]` — it records the matched prefix in `root_path` and leaves the path alone, so under the mount the value reads `/panel/static/app.css` and **the skip never fired**: every asset on every page resolved a session of its own, and a cold cache meant several concurrent backend lookups per page load against a ~20-session Oracle budget. The test now runs against the path within the mount. Separately, the sid cache cleared itself outright when full — and since any visitor can set their cookie to any hex string, each junk value caches a resolved absence, so filling the cache and clearing it evicted every **real** session too and sent the whole fleet back to the backend. Eviction now takes expired entries, then resolved absences, then the entries closest to expiry.

## 🐳 Node agent (container host)

The node agent runs on the Docker host behind one shared bearer token and performs
**no ownership check** — the application tier is the only authorization layer (see
Authorization / RBAC). These are the node-side controls that stop a hostile bot or a
crafted request from escaping its container or steering the daemon. Audited this pass.

| Security | Where | Verdict |
|---|---|---|
| Container isolation | `docker_runtime.py`, `container_spec.py` | **PASS** — every managed and install container is created with `cap_drop=["ALL"]`, `security_opt=["no-new-privileges:true"]`, `pids_limit=128`, a hard `mem_limit` with `memswap_limit == mem_limit` (swap disabled), `nano_cpus` cap, and a non-root `user`. Startup as `/bin/sh -lc <cmd>` reaches Docker as an **argv list** (the daemon API, not a host shell) and runs inside the user's own sandbox — no host-shell interpolation anywhere. **Fixed this pass:** `run_install` passed the `logging` kwarg to `containers.create()` with none of the try/except-and-retry that `create()` wraps the identical kwarg in, so a docker-py build that rejects it would fail *every* dependency install while `create()` recovered — the two paths now degrade identically (drop the log driver, keep the install). |
| Image / catalog trust | `catalog.py`, `install_scripts.py` | **PASS** — `resolve_image()` rejects an unknown runtime or version with `ValueError` and never falls through to an arbitrary pull; `build_container_spec`'s `image` arg always originates from that allowlist or from an existing container's own image, so `images.pull` cannot be steered to an attacker image. Install scripts are 100% static literals selected by key — no runtime version, package name, URL or server name is ever interpolated into a script body; the unknown-runtime default is the shell no-op `true`. |
| Path traversal / symlink escape | `storage.py` | **PASS** — `resolve_server_path` normalises `\`→`/`, rejects absolute paths (Windows-absolute and leading-`/`), then `.resolve()` canonicalises (following any symlink) and `relative_to(root)` rejects anything that lands outside the server root, so a symlink pointing out of the tree is caught by the resolve. Every read/list/size/chown path uses `follow_symlinks=False` / `os.walk(followlinks=False)` / `lchown` explicitly. Listing is capped at 5000 entries and the editor read at 2 MB. A residual write-path TOCTOU (a directory component swapped for a symlink between resolve and write) is the same standard the app tier's file manager uses; closing it needs `O_NOFOLLOW`/`openat2` plumbing Python does not portably expose — flagged, not half-fixed on a live host. |
| Bind exposure | `run.py`, `asgi_panel.py`, `main.py` | **PASS** **[ACTIVE]** — the node port is full control of the host Docker daemon behind one token, so a `0.0.0.0` bind logs an explicit interface/firewall warning (`run.py`). **Corrected this pass — the previous wording was false for the frontend.** Three tiers **refuse** to start on a wildcard bind: the panel (`asgi_panel._bind_host`, :181-201), and the backend and engine under gunicorn (`main._tier_cmd`, the refusal at :154-170). The frontend does **not**, and that is deliberate, not an oversight: it is the one browser-facing WSGI tier and it is meant to be public. Its `_GUNICORN_TIERS` entry hardcodes `"0.0.0.0"` with `None` for its host-env field (`main.py:117`), the refusal sits inside `if host_var:` (`:154`) and so never runs for it, and `:180` emits `--bind 0.0.0.0:5000` unconditionally. Its own launcher says the same thing in as many words (`start_frontend.py`: "This is the only tier bound to 0.0.0.0"). The panel is not exempted despite being browser-facing, because it has no login of its own and is only ever reached through whatever fronts the site on that host. |
| Docker call timeouts | `docker_runtime.py` | **PASS** — every Docker API call carries a deadline (`NODE_DOCKER_TIMEOUT`, floor 10s) so a wedged daemon or slow registry cannot pin a waitress thread indefinitely and starve `/health`; installs are additionally bounded by `INSTALL_TIMEOUT_SECONDS` with a kill-and-report path, and orphaned install containers are reaped at startup. |

## 🔐 Sensitive data

| Security | Where | Verdict |
|---|---|---|
| AES-256-GCM | backend, before storing selected fields | **PASS as a capability, PARTIAL in use.** Two at-rest formats are always *read* — Fernet (`gAAAAA`) and AES-256-GCM (`gcm1.`, 12-byte nonce) — and `ENCRYPTION_FORMAT` selects which is *written*; it still defaults to `fernet`, so GCM is available and readable but not yet the written format. The GCM key is domain-separated: `sha256(b"dc-hostfnal/aes256gcm/v1|" + fernet_material)`. AAD is supported by `encrypt()` but no column passes a context, which is why `rekey_encrypted.py` correctly pins `GCM_CONTEXT = ""` — verified this pass, since a context adopted in `database.py` without the identical string there would make the column unrecoverable on the next rotation. `panel_users.username` is still **plaintext**; encrypting it is a live migration touching a unique index on `lower(username)`, three `func.lower` comparison sites, an order-by that cannot sort ciphertext, and a backfill with old code serving on both instances mid-rollout. ## Honest limitations

These are real and were left undone deliberately, not overlooked.

1. **Least-privilege DB user** — needs a production migration and a connection-string change on both instances. Cannot be validated without connecting to the live ATP.
2. **`panel_users.username` at rest** — see the AES-256-GCM row. A functional unique index on `lower(ciphertext)` and an order-by that cannot sort ciphertext make this a schema migration, not an edit.
3. **SRI** — impossible for rotating ad-network bodies; there is no other cross-origin subresource.
4. **Uploads are buffered whole** — `await uploaded_zip.read()` peaks around 1.3 GB RSS for one 150 MB upload. Streaming multipart is a protocol change on both the panel and the node agent, so it is a feature, not a fix.
5. **Rate limits are per-process unless `RATELIMIT_STORAGE_URI` is set.** With two instances × N workers, every worker grants its own full allowance. The startup warning at `frontend.py:517` already says so, and it applies to the new per-account login limit too — that limit is only fleet-wide when the shared store is configured.
6. **`docker-compose.yml:9` still binds `0.0.0.0`** — a deployment decision, left for the operator.
7. **node-agent `requirements.txt` is unpinned** — pinning it is a supply-chain improvement but changes what installs on the next deploy, so it is the operator's call.

## Controls that are inert by default

Everything in this list is code that is present, correct and doing nothing until
the named variable is set. Nothing here is a bug; the bug was documenting them as
though they were running. Names only — no value from a live `.env` appears in this
file.

| Set this | To activate | Precondition / caution |
|---|---|---|
| `TURNSTILE_SITE_KEY` **and** `TURNSTILE_SECRET_KEY` | The only thing that creates a CAPTCHA anywhere in this stack: the login and register-step-1 pre-KDF guards, and `edge_gate`'s site-entry interstitial. | **Both** are required — `enabled()` refuses a half-configured pair, because a widget whose answer nothing can check looks protected and is not (`turnstile.py:81-90`). `TURNSTILE_ENABLED` already defaults to `1`, so the keys are the whole switch. Consider `TURNSTILE_FAIL_CLOSED=1` only with eyes open: it converts a Cloudflare outage into a total sign-in outage. |
| `RATELIMIT_STORAGE_URI` | Makes every flask-limiter bucket fleet-wide instead of per worker per instance. Until it is set, `10 per minute` is `10 per minute per worker`. | Nothing else; `in_memory_fallback_enabled=True` (`frontend.py:615`) means an unreachable store degrades rather than fails. Does **not** affect the panel limiter or `edge_gate` — both are per-process by construction. |
| `CF_TRUSTED_IPS` | Extends the trusted-peer set beyond Cloudflare's published ranges, which is what makes `CF-Connecting-IP`, `CF-Verified-Bot` and `CF-Browser-Integrity` believed at all when the balancer's own range fronts the app (`cf_edge.py`, consumed at `frontend.py:1252-1269` and `edge_gate.py:301`, `:336`). | Unset, those headers are discarded from an untrusted peer — correct, but it means the CF-verified-bot path never fires and `_is_search_crawler()` falls back to the user-agent test. |
| `GATE_HARD_CLOSE=1` | Lets the tier drop its listening socket under sustained flood and rebind after `GATE_CLOSE_COOLDOWN`. | **Waitress only.** Only `serve()`'s hard-close path registers a listener controller (`frontend.py:3070`); under gunicorn nothing polls `should_be_closed()`, so the flag still withdraws nothing — it now refuses to arm and warns once that it did nothing, rather than logging a close it never performed (`frontend.py:3059-3126` vs `wsgi_frontend.py`). |
| `PANEL_LIMIT_MAX_REQUESTS` | Recycles the panel worker after N requests, capping the blast radius of a slow per-request leak. Default `0` = disabled. | Not a rate limit — the panel's request ceilings are hardcoded (see the Rate-limiting row). Only read on the uvicorn `serve()` path (`asgi_panel.py:239`), so it is inert under gunicorn, and `main.py` does not restart a tier that exits, so a finite value there kills the panel rather than recycling it. |

**Do not set `GATE_MODE=always` before `CF_TRUSTED_IPS` pins the load-balancer
range.** `always` challenges every unsolved HTML navigation, and the only thing
at that layer that spares a crawler is the verified-bot exemption
(`_cf_verified_bot`, `:352-357`) — the path exemptions at `:107` and `:113-116`
keep `/robots.txt`, `/sitemap.xml` and `/feed.xml` answering, and nothing more.
That exemption is **[INERT: `CF_TRUSTED_IPS`]**: it believes `CF-Verified-Bot`
only from a socket peer on `HEADER_PEER_NETWORKS`, which while unpinned is the
published Cloudflare list, and the peer here is the balancer. So until the
balancer range is pinned, Googlebot fetching any HTML page still gets an
interstitial it cannot solve and the site deindexes — the conclusion has not
changed, only the reason it holds. Treat `suspicious` (the default) as the only
mode this stack is currently shaped for.

## Consequence of leaving `/admin` untouched

All seven files tracked in `admin/VENDOR.json` — `creds.py`, `crypto_util.py`, `database.py`, `engine_client.py`, `error_codes.py`, `internal_auth.py`, `reviews_db.py` — are byte-identical vendored copies of `app/`'s, and `app/` has now been edited. `admin/start.py:_warn_on_vendor_drift` (:35, called at :56) will therefore print a sha256 drift warning on startup. **It only warns; it never fails.** Re-syncing is one command (`cd admin && python sync_from_app.py --repo ../app`, then `--check`), but it modifies `/admin`, so it was not run.
