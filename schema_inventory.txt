    username_lookup_hash     VARCHAR2(64)   UNIQUE,

    display_name             VARCHAR2(255),

    github_verified          VARCHAR2(5)    DEFAULT '0',

    server_id     VARCHAR(64) PRIMARY KEY,

    node_ip       VARCHAR(255) NOT NULL DEFAULT '',

================================================================================
 NOTES ON THE MISMATCHES
================================================================================
 The MISMATCH rows are two DIFFERENT tables that happen to share a column NAME;
 none of them are a foreign-key pair enforced by the DB, so nothing breaks today.
 They are cosmetic/consistency drift EXCEPT:

  * node_id : NUMBER in panel_servers vs VARCHAR(64) in the MySQL delete/retire
    queue. These DO refer to the same node identity across stores, so a lookup
    that carries a node id from one to the other must cast. Verify the join code
    stringifies consistently.

  * created_at : VARCHAR2(50) in the database.py Oracle tables but native DATE in
    nodes/panel_*. Mixed representation of "when" across the same ATP. Sorting /
    range purges rely on lexicographic ISO strings on one side and real dates on
    the other.

  * ip_address 255 vs 45, name 100/255/500, token_enc 500 vs 2000, last_error
    500 vs 1000 : pure width drift. The SMALLER one is the risk — an encrypted
    token that fits nodes(2000) would be truncated if ever written to bots(500).

 No two tables define the SAME column twice within one table (no real duplicate
 within a single CREATE). All "duplicates" are cross-table name reuse.
